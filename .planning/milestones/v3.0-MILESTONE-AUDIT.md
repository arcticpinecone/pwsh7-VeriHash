## 3. Defects Found During the Audit

Three defects, all the same failure class: **a producer emitting N values, a consumer
written for N−1, and a fallback absorbing the difference without complaint.** The
codebase had already named this pattern as CMP-14 before these instances were found.

### 3a. `Test-All.ps1` could never fail (severity: high)

The harness built its `PesterConfiguration` without `Run.PassThru`, so `Invoke-Pester`
returned nothing. It then read `FailedCount` off `$null`, evaluated `$null -gt 0` to
`$false`, and took its success branch on **every** run — printing `All  tests PASSED`
(the doubled space being the empty count) and exiting 0 with failing tests.

This is the most serious finding because it sits above the others: a broken quality gate
cannot report that the quality gate is broken, and the pre-commit hook depends on it.

**Fixed and proved both directions.** With a deliberately failing canary test, the old
code exited 0 reporting success; the fixed code exits 1 with `1 failed, 371 passed`. A
null result is now treated as inconclusive rather than as success.

### 3b. Manifest summary undercounted rejected entries (severity: moderate)

`Test-VeriHashManifest` produced five entry statuses and counted three. `parse-error` and
`traversal-rejected` were included in `Total` but in no bucket, so a manifest with two
rejected paths reported `8/10 passed, 0 mismatch, 0 missing` — and the two entries missing
from the arithmetic were precisely the ones the path-traversal guard had rejected.

Fixed by counting via a single pass that increments exactly one bucket per entry, with an
unmapped status throwing rather than vanishing. `Rejected` is its own bucket rather than
folded into `Failed`, because a traversal rejection is a security event, not a hash
disagreement.

### 3c. Unsupported hex reported as an empty clipboard (CMP-10, severity: moderate)

Covered as a requirement rather than a bug, but the same shape: `Read-ClipboardHash`
returned `$null` for a 56- or 96-character paste, which rendered as "nothing
recognizable". A user who deliberately copied a vendor's SHA-384 was told their clipboard
was empty, inviting them to read silence as approval.

## 4. Process Findings

These do not affect the verdict but are the reason this milestone felt less complete than
it was.

### 4a. Phase 9 was executed without plan documents

Phases 6 and 7 have plan files (`06-01`, `06-02`, `07-01`). Phase 9's three plans —
referenced by ID in every commit message — have none. The work was driven directly from
`.planning/notes/comparator-algorithm-exploration.md`.

The exploration note is unusually thorough and the commits are atomic and well-described,
so nothing was lost in practice. But phase status could not be read off the planning
directory, which contributed directly to 4b.

### 4b. Documentation understated the milestone by a wide margin

At the start of this audit:

- Every `SIDE-*` and `FMT-*` requirement was unticked, though both phases had shipped
  months earlier and their code and tests were present and green.
- Phase 9 was absent from ROADMAP.md entirely, and its 19 CMP requirements were never
  added to the traceability table.
- STATE.md reported **67% complete** when only one feature (Phase 8) genuinely remained.

The percentage was computed over phases, which distorts whenever phases differ in size.
All corrected, with the drift itself recorded in REQUIREMENTS.md rather than silently
rewritten.

### 4c. CI was not exercising the suite developers run

The workflow pinned Pester to `<=5.99` while every local run and `Test-All.ps1` used
Pester 6.1. A green CI therefore said nothing reliable about the suite people actually
run. The workflow also could not trigger on changes to itself, so a CI fix could never be
validated by pushing it. Both fixed in `ec3d72e`.

## 6. Deferred Work

**Phase 8 — Manifest Spot-Check (SPOT-01..05).** Deferred 2026-08-16 by explicit decision.
Spot-check is additive: nothing VeriHash reports today is wrong without it, and a user can
already verify a whole manifest. Holding a release containing correctness fixes that are
done, in exchange for convenience that is not started, is the wrong trade. Requirements
are preserved in REQUIREMENTS.md → Future Requirements, not deleted.

32/32 in-scope requirements satisfied and tested. 371 tests green, analyzer clean, both
